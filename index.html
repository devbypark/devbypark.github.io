01 / FDE FIT

FDE에게 요구되는 일,
제가 해 온 일.

직함은 Solution Engineer이지만,
아래 일은 고객 프로젝트에서 직접 수행했습니다.

  1. 01고객 요구를 기술 목표로 바꾸기

    API만 쓰는 고객에게 중요한 것은 처리량이 아니라 한 건의 응답 시간이었습니다. 이를 개선 목표로 잡고 AI 엔지니어와 함께 건당 20–30초를 워밍업 후 약 2–3초로 줄였습니다.

  2. 02낯선 제약 안에서 BMT 수행하기

    평가 문서를 미리 알 수 없는 조건이라, 처음 보는 문서도 바로 검수할 수 있는 평가 흐름을 먼저 만들었습니다. 현장에서는 라벨링·GT 생성·프롬프트 수정을 직접 하며 BMT를 진행했습니다.

  3. 03프런트엔드부터 모델 서빙까지 구현하기

    문서 접수·추출·검수·마스킹·외부 연동을 하나의 제품 흐름으로 묶어 프런트엔드와 백엔드를 단독 개발하고, 모델과 서빙 작업에도 참여했습니다.

  4. 04평가와 계측으로 판단하기

    정답 데이터와 구간별 처리 시간을 기준으로 판단했습니다. 200페이지 사전 검증에서 실패 0건, weighted recall 97.2%(IoU 0.5 기준)를 확인했고, 처리 속도가 개선되더라도 검출 정확도가 기준에 미치지 못하는 설정은 채택하지 않았습니다.

  5. 05고객 시스템과 일정에 맞춰 연동하기

    고객의 RPA 개발이 추출 기능을 기다리지 않도록, 연동에 필요한 API 필드 명세와 입력 검증을 먼저 제공하고 신규 필드 추출은 뒤이어 넘겼습니다.이전 회사에서는 파트너 개발자와 결제 요청·콜백·웹훅 규격을 직접 협의해 연동 API를 개발했습니다.

  6. 06폐쇄망에 설치하고 배포 이후까지 책임지기

    6건 모두 폐쇄망이라 드라이버부터 모델 파일까지 오프라인 번들로 설치했습니다. 구축 후 장애가 났을 때도 원인을 직접 찾아 복구하고, 재발하지 않도록 다음 배포 패키지에 반영했습니다.

  7. 07LLM 출력을 믿을 수 있게 만들기

    스키마의 값 패턴을 모델 서버가 다르게 해석해 한국어 이름이 로마자로 출력되던 문제는, 패턴을 저장할 때 모델 서버 기준으로 미리 검사하도록 바꿔 막았습니다. 지연 개선 설정이 일으킨 모델 출력 퇴화는 평가셋 681건으로 잡아 원인을 확인하고 되돌렸습니다.

문서 AI에서 고객의 목표를 정의하고, 평가 기준을 세우고, 추론을 최적화하고, 고객 시스템에 연동해 운영한 경험은 다양한 도메인의 AI 제품에서도 활용할 수 있다고 생각합니다.

04 / HOW I ENGAGE

기술보다 먼저, 맥락을 이해하기.

고객 프로젝트를 끝까지 가져가는 네 단계.
각 단계는 실제 사례에서 가져왔습니다.

  1. 01

    고객의 사용 방식에서 목표를 정합니다

    단건 API를 쓰는 고객은 처리량보다 응답 시간을, NAS에 문서를 보관하는 고객은 수집 경로를, RPA 일정이 걸린 고객은 제공 시점을 먼저 다뤘습니다.

    SCOPE
  2. 02

    GT와 계측으로 먼저 증명합니다

    정답 데이터와 처리 구간별 시간으로 오류와 병목을 확인하고, 품질과 속도를 함께 비교해 처리 코드·서빙 설정·프롬프트를 고릅니다.

    PROVE
  3. 03

    고객 환경에 설치할 수 있게 만듭니다

    애플리케이션·워커·GPU 서비스의 배포 구성과 DB 마이그레이션, 권한·무결성 검사, 사전 점검 절차를 정리해 현장에 배포합니다.

    SHIP
  4. 04

    운영에서 나온 요구를 제품으로 되돌립니다

    구축 이후의 유지보수를 이어가고, 고객 미팅과 현장 피드백을 스키마·검수 화면·수집 경로 같은 제품 개선으로 연결합니다.

    OPERATE

모델의 동작만큼, 실제 환경에서의 배포와 운영을 중요하게 생각합니다.
